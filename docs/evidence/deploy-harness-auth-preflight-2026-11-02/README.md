## The incident this closes (measured 2026-11-02, not imagined)

A `--restart-only` movement ran with `/home/team/shared/.demo-admin-password` holding a stale
33-character password while the real one was 20. The login answered 401, so `TOK` was empty; every
step-5 probe ran unauthenticated; the roster answered 401; three inline `python3` blocks hit
`json.load` on the 401 body and printed tracebacks; the settlement check was handed an error payload
and correctly answered rc=2 (CANNOT-JUDGE); and the harness's own verdict line read
**`RED VERIFICATION (settlement check rc=2)`** — naming the settlement check, which was never at fault.

`control-old-vs-new.out` reproduces that, using the PRE-FIX step 5 and verdict block extracted byte
for byte from `fff847b` and run with a deliberately wrong credential. It is not a retelling:

    demo login token chars: 0 (expect >100)
    roster: 401
    Traceback (most recent call last):            (x3 — KeyError: 0, AttributeError, TypeError)
    CANNOT-JUDGE: .../settlement.json carries no document content - nothing to judge
    FAIL: the settlement check is RED (rc=2)
    === cutover finished ... WITH A RED VERIFICATION (settlement check rc=2) ===
      OLD PATH EXIT CODE: 1

## What changed

1. **A credential/token preflight that runs before ANY judgment.** `authenticate()` asserts, in
   order: the credential file exists, is readable and is not empty; the login yields a token of the
   expected shape (>100 characters); **an authenticated read accepts that token**. Each failure
   names **AUTHENTICATION** as the cause, prints a character **count** (never the value) and the file
   it read, and exits **3**. Nothing in step 5 can run after a failed preflight.
2. **The token is proved, not assumed.** The roster read in the preflight *is* the read step 5
   reports on, so the proof and the reported count are one measurement. Its **401 is an
   authentication failure and nothing else** — named as such, never rendered as a settlement or data
   problem.
3. **No tracebacks as defect reports.** Every inline `python3` that parses a response body is
   preceded by an HTTP-status check and wrapped so a bad body yields
   `CANNOT-JUDGE: <what it was> (<status code>)` and exit **4**. The settlement check is handed its
   document only after the status is checked, and its rc=2 is now reported as CANNOT-JUDGE rather
   than "RED".
4. **`--preflight` mode** — read the credential file, log in, make one authenticated read, print the
   counts, exit. No git, no build, no restart, no database write. Honours `ANTUM_PW_FILE`.
5. The credential **file** is also refused at the very start of a movement, before the fetch, the
   build and the restart — no point taking the product down to find out.
6. `--help` now prints the header block by anchoring on the first line of code rather than a fixed
   `sed -n '2,32p'`, which the installer's provenance block broke on the host copy.

**Exit codes:** `0` the run's own verdict · `1` a judged red · `2` usage · `3` AUTHENTICATION ·
`4` CANNOT-JUDGE.

## The control: the preflight is the load-bearing thing

`bash docs/evidence/deploy-harness-auth-preflight-2026-11-02/control.sh fff847b`

It extracts the PRE-FIX step 5 and verdict block from `fff847b` with `git show | awk` between two
anchors and runs them as that revision's own shell code with a wrong credential; then runs the new
`--preflight` with the same wrong credential. It asserts the old path printed a traceback and named
`settlement check rc=`, and that the new path exits 3 naming AUTHENTICATION and reaches no settlement
verdict. Exit 0 = the control held. **Measured: it holds** (`CONTROL_EXIT=0`).

Bypassing the preflight is therefore sufficient to restore the old behaviour — the preflight, not
some other line, is what stops the wrong-credential run from reaching judgment.

## The red I did NOT fix, stated plainly

`python3 scripts/check-all.py` on this branch: **10 OK / 2 BROKEN / 9 skipped, exit 1** — the same
worktree at `fff847b` gave **12 OK / 0 BROKEN, exit 0** before the change.

Both reds come from one finding:

    [BROKEN] reachability-report  exit=1
      GET /api/login at scripts/deploy-main.sh:177
      1 NEW finding(s)
    [BROKEN] suite  exit=1   server suite: tests 427, suites 68, pass 424, fail 3

The reachability scanner classifies the new login call in `authenticate()` as a client call that
names no route. Note it reports the method as **GET** although that line is the POST login — the
scanner's method detection is reading a different shape than the pre-fix script's (which put
`-X POST` and the URL on continuation lines too, and was not flagged). I did not find the root cause
before the session budget ran out, and I did not weaken the check or move a plant to fit it. The
next step is to read the caller detector (it is not in `scripts/reachability-report.js`; that file
only consumes it) and either re-shape the call or fix the detector.
