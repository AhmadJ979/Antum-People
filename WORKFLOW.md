## Submission Gate — every one of these must hold before you report
Owner-confirmed, 2026-10-02. These are the five reasons submissions have come back; check each against your own branch before you write a result.

1. **Read remote state before any status claim.** Run `git fetch origin` and `git log --oneline -1 origin/main` in this session. A claim about a branch, a PR or `main` that you did not read this session is an inaccurate report, not a status update (rules 12, 13).
2. **Build proof on every client-touching PR.** `cd client && npm run build` must exit 0 **and** emit `dist` — paste the raw tail (the `dist/assets/index-*.js` line and the exit code). `npm run dev` is never evidence: it skips `tsc -b`, which is the half that catches a file that does not parse (rule 15).
3. **No pinned figures.** Every number comes from the engine or the seed's own computation path. Never hardcode a value to make a screen agree with a record; report the disagreement with the arithmetic behind both sides instead (rule 16).
4. **No invented directives.** If an instruction is unclear, ask the lead. Never write a comment, commit message or result that attributes an instruction to the owner or the lead unless it appears in a task, an inbox message, or this file (rule 16).
5. **One PR per task.** One branch from current `main`, one PR. No duplicates, no `-v2`, no second submission of the same work (rules 1, 13).

## Development Process
1.  **Branching:** All new features and fixes should be developed on feature branches.
2.  **Pull Requests:** Once work is complete, create a pull request (PR) to the `main` branch.
3.  **Review:** The lead (agent-lead) will review the PR.
4.  **Merge:** After approval, the **owner (admin) merges** the PR. **The lead reviews and approves but does not merge, and no member merges their own work** — open the PR, report the link, and the owner merges (owner instruction, 2026-10-07; supersedes the earlier "the lead will merge" line).

## Task Management
-   Use `create_task` and `assign_task` to manage the kanban board.
-   Always call `finish_task` when work is ready for review.
-   Include a detailed summary in the `result` field when finishing a task.

## Communication
-   Use `send_message` for follow-up questions or status updates.
-   Keep the lead informed of any blockers.

## Hard Rules (learned from rejected work — violating these gets a task sent back)
1.  **One branch per task, no duplicates.** Consolidate everything for a task onto a single branch cut from current `origin/main`. Near-duplicate branches (`-v2`, `-revised`, `-final`) are not acceptable deliverables.
2.  **A real PR, or it isn't submitted.** Run `gh pr create --base main` and report the returned PR URL. A `github.com/.../compare/...` link is **not** a pull request and will be rejected.
3.  **The branch you name must exist.** Confirm with `git ls-remote --heads origin <branch>` before writing it into your result. Reporting a branch that does not exist is treated as an inaccurate report.
4.  **No secrets and no employee data, ever, in a repo file or in a task result.** Never write `JWT_SECRET`, `ENCRYPTION_KEY`, passwords, tokens or key values — not even old/dev ones, not even a fragment of one — into code, docs, reports, logs or your `result` summary. The same goes for real employee data: never paste a National ID / Iqama (encrypted *or* decrypted), salary, email or EOSB figure into a summary, report or commit. Describe what you checked, not the values.
5.  **Credentials are lead-managed.** Do not set, reset or rotate passwords, the `users` table or encryption keys. Do not set a demo/demo-admin password yourself. If a credential is needed, ask the lead.
6.  **Don't break callers.** If you change what a module exports (e.g. `server/auth.js`), update every caller in the *same* branch and prove it: an authenticated route returns 200 with a valid token and 401 without one.
7.  **Scripts point at the deployed tree.** Anything committed under `scripts/` must operate on `/home/team/shared/probable-octo-sniffle` — never a personal clone, never personal log paths.
8.  **Verify on the public URL.** Editing, building or merging is not proof. State what you observed: HTTP status, page title, and the result of a bad-credential login.
9.  **Never erase history.** `README.md` keeps the rebrand-history line exactly as it is — "On 2026-09-17, this product was rebranded from **VantageHR** to **Antum** / **Antum People**." The old name plus its date stays: it is honest record-keeping, not a leftover to scrub. Renaming or removing it is a regression.
10. **Do not read or use the demo password yourself.** It is lead-managed. Verify the rejection path (wrong password → 401) on your own; if a successful-login check is needed, ask the lead to run it and report the result.
11. **Rework means the commit moved.** When a task comes back for changes, the resubmission must be a *different* commit. Paste the new head SHA (`git log --oneline -1` on the branch, and the PR head SHA) beside your claims. Re-submitting the same commit — even under a new branch or PR number — is not a fix and will be rejected unread. If you believe the previous rejection was wrong, say so and argue it; do not silently re-send.
12. **Report only what you measured.** Every state in a result — merged, live, row counts, word counts, file changed, task status — must be read off the artifact in this session (`git fetch && git log --oneline -1 origin/main`, `wc -w`, `ls -l`, `team-db "SELECT status FROM tasks WHERE id LIKE '<id>%'"`), never recalled. A given number that does not match the artifact costs credibility on everything else in the submission. Saying "I did X" when the artifact shows X was not done is the worst failure mode this team has, and it has happened repeatedly.

13. **Check remote state before you create anything.** Opening a PR is the last step, not the first. Before branching, run `git fetch origin --prune`; before opening a PR, run `gh pr list --state open --json number,headRefName,title` and confirm your task does not already have one. If a PR for your task is already open, **push to its existing branch** — do not create a second branch, a second PR, or a `-v2` variant. If your branch was deleted or closed externally, create exactly one new branch from current `origin/main` and say in your result that the previous one was closed. Two open PRs for one task is a failed submission regardless of the code quality, and it strands work: verified fixes on a branch nobody can see are worth nothing.
14. **You cannot test against the live deployment; use your own scratch instance.** For any change to auth, the database or the API, stand up a scratch instance (own port, own scratch `PRODUCT_DB_PATH`, own temporary credential hash) and test there. Never set, read or rotate the live demo credential (rule 10), never start or restart the live server, and never re-arm the watchdog — the lead owns the live tree and the cutover.
15. **Client changes carry build proof — owner's standing rule (2026-09-28).** Any PR that touches client code must state, in the submission, that **`cd client && npm run build` exits 0 and `dist` was emitted** — paste the raw tail of the build output (the `dist/assets/index-*.js` line and the exit code). The owner checks this on every client-touching PR before merging, and the lead will not merge one without it. **Owner ratification (2026-09-28):** this gate is correct and the lead enforces it *without waiting for the owner's sign-off* — "enforce it without waiting for me." An unreviewed PR, or a client-touching PR with no build proof, is not merged, whoever opened it.
`npm run dev` is **not** evidence: it skips the `tsc -b` half of the build, which is the half that catches a file that does not parse. This rule exists because a merged PR with eight backslash-escaped quotes in a JSX attribute reached `main`, failed `tsc -b`, produced no `dist`, and left the demo client unshippable until it was repaired.

16. **Never pin a number to make a screen agree — and never invent an instruction.** Every figure the demo shows must come from the engine, or from the seed's computation path for that figure. Hardcoding a value to make a statement match a record (`if (emp.id === 'demo-emp-sarah') { eosbAccrued = 19794.66; }`) is fabrication, not a fix: the screen then displays a number the compliance engine can never produce, which is the same defect class as a hand-written checklist. When two sources disagree, **report the discrepancy and the arithmetic behind each side** and let the lead decide which source is wrong — never force them into agreement. For the same reason, never write a comment, commit message or result that attributes a directive to the owner or the lead unless it appears in a task description, an inbox message, or this file. If you are unsure what was asked, ask.

17. **A credential or auth failure comes to the lead at once — do not retry your way around it (2026-10-06).** The team's GitHub credential is lead-managed and expires silently; when it does, **every** member's push fails, so no amount of retrying, re-branching or re-creating the repo state will help. If `git push` or `gh pr create` fails with an authentication error, or `gh auth status` reports an invalid token: **message the lead immediately with the exact error, and stop** — do not retry more than once, do not attempt an alternate credential, and do not treat it as your own troubleshooting problem. If the change is otherwise ready, say so and leave the work on your branch (and, if useful, a patch in `/home/team/shared`) so it can land the moment the credential is refreshed. Keep working on anything that is not blocked. This rule exists because an expired token cost the team two full cycles on 2026-10-06, with a member retrying a push that could not succeed rather than reporting it.
18. **A rejection listing several items is one instruction, not several rounds (2026-10-06).** When the lead sends a task back with more than one required change, **address all of them in the same resubmission** — or, if you believe one is wrong or cannot be done, say so explicitly in your result and argue it. Do not fix the easy item, resubmit, and leave the rest untouched: that costs a whole cycle per item and it reads as ignoring feedback. The same applies in reverse and is worth knowing: if the resubmission's commit head has **not** moved, say plainly that you are arguing the previous rejection rather than silently re-sending it (rule 11). This rule exists because a two-item rejection on 2026-10-06 came back with the second item unaddressed and unmentioned, costing an extra cycle on a one-sentence fix.

19. **Evidence is about the tree that will merge — not the branch you built on (2026-10-07, lead-enforced after the owner returned a stub as a request change).** If `main` has moved since you cut your branch, an evidence pass on the branch alone describes a tree nobody will run: on 2026-10-07 a browser pass reported "AE cases only" on a branch whose own seed created no pre-boarding cases at all, because the seed had merged to `main` after the branch was cut. Build the scratch rig from the **merge result** — `git merge-tree --write-tree origin/main <branch>`, then apply your diff onto a fresh `origin/main` worktree — and prove it is the merge result by comparing blob hashes (`git hash-object` on the rig's file vs `git rev-parse <branch>:<path>`), not by trusting the recipe. Name the base commit you merged onto in the evidence, not just your branch.
    **Scope a PR against its own base — never a cross-PR range (2026-10-09).** `git diff <merge-base>..<branch>`, or a merge commit against its **first parent**, is the PR's scope. A range that spans two merges (`501d5fa..35cbaa1`) silently attributes another PR's files to your diff — on 2026-10-09 that produced "20 files including `client/src/App.tsx`" for a docs-only PR whose real scope was one file. Check the base before you quote a file count.
    A transcript that shows a run which did not happen is **worse than no transcript**: an `ECONNREFUSED` stub, a file ending "NOT YET DONE", or output from a server that never started reads as proof while proving nothing. If a scratch instance will not come up, fix the instance **before** you write the evidence file. If you have already published a false artifact, **withdraw it inside the file** — state that it was a stub and why it could not have been evidence — rather than quietly replacing it with a good one.
    **A synthetic `element.click()` does not switch this app's nav tab; a real click by accessible ref does (2026-10-09).** That single mechanism produced a rig report of "no case rows" on a healthy product — before you report the product broken, click the way a person does and re-read.
20. **A "PR awaiting your action" notice is not an instruction to push (2026-10-09, after two ghost commits in one morning).** The platform's task template tells the author to push a new commit to the same branch and call merge — but the **owner merges**, and by the time the notice reaches you the row may already be `done` with the PR merged and the branch deleted. Check the row's status (`team-db "SELECT status FROM tasks WHERE id LIKE '<id>%'"`) and whether your tip is an ancestor of `origin/main` (`git merge-base --is-ancestor <tip> origin/main`) **before** doing anything. If it is merged, the correct delivery is a **measurement** — merged SHA, review count, files byte-identical between your tip and the merge result — not a commit. Creating a branch again to push a no-op is a ghost commit and wastes a cycle.
21. **The credential can die as a hang, not only as an error (2026-10-09).** An empty credential store now makes `git credential fill` **prompt** (`Username for 'https://github.com':`) instead of failing, and inside a compound `&&` command that prompt looks exactly like a slow network call — the command simply hangs. Never run a git or `gh` command that can prompt inside a compound command; if one hangs, interrupt it. On any auth failure or hang: call `get_git_credentials`, retry **once**, and if it still fails message the lead with the exact error (rule 17). Reading never depends on the credential — `git fetch https://github.com/...` works anonymously, so measure with git first and report.
22. **Deploy what `origin/main` is, not what the plan remembers (2026-10-09).** A recorded hash goes stale between revisions: on 2026-10-09 the plan said `main` = `25a3af0` while `origin/main` was already `2028894`, because the owner had merged a docs PR after the revision was written. Before moving the deployed tree: `git fetch origin main`, read `git log --oneline -1 FETCH_HEAD`, check `git merge-base --is-ancestor <recorded-hash> FETCH_HEAD`, and **name the delta** you are about to deploy. A cutover that deploys an unnamed delta cannot be reviewed, and deploying *behind* `origin/main` silently un-ships merged work.
23. **A self-check value is read after the last commit, and a submission is frozen (2026-10-09).** Two failures in one round: a wall-clock time written from memory (12:32, later corrected to the measured 12:05), and a self-check hash published for a commit that was no longer the tip because a fourth commit landed after `finish_task`. Any hash, count or clock time you publish as a check for someone else must be read off the artifact as the **final** state of your branch — re-derive it immediately before you submit. And do **not** push to a branch that is under review: a PR the owner is asked to merge must not be a moving target. If you find something after submitting, say so and hold it for the next round.
24. **If your own evidence refutes the premise of the change you were asked to make, withdraw the change and deliver the finding (2026-10-09).** A row can be written as "fix X — or, if no reachable path exists, report it" and the investigation may come back: no reachable path exists. That answers the row; it is a finding, not a build. On 2026-10-09 the exit-intake row produced a working opener and, in the same pass, the fact that the route has exactly one caller and it is the unreachable control — so the author **closed his own PR** (#112, unmerged, code preserved at `refs/pull/112/head`), opened a finding-only PR (#113), and said in the PR comment which branch his own evidence had landed on. Do not ship a change whose justification your measurements contradict, and do not bolt a control onto a surface you chose yourself when placement is the open question. Report the state, name the ref that actually exists, and leave the decision to be made.
25. **A screenshot is evidence only of the page it came from, and it must carry that page's identity (2026-10-09, task `f916c9ff`, row `2c37f2da`).** The All-chip evidence pack shipped a shot captioned "the same moment with the fix" that in fact depicted the **defect**: it differed from the before-pass frame by 4 bytes and 760 pixels, every one of them in the scrollbar track. The same pass's machine-scored samples held the fixed behaviour on every tick (0 defect ticks against the before pass's 11), so the shot — not the fix — was the false artifact, and it was caught by a reviewer, not by us. Three conditions now apply to any captured screen evidence:
    - **One browser session per bundle.** Never swap a bundle, a tree or a deployed surface under a live browser session and keep using it: the session's page can still be the old one while the reads and the shots run against the new one. Running both halves of a before/after comparison through one session across a swap is exactly what produced the false artifact.
    - **Every screenshot records its own identity, taken in the same breath as the shot:** the page's own script `src` (`/assets/index-…js`, with its measured size and md5 where they can be had) and the panel's DOM reading. A shot that carries its own bundle name can be checked by a reader; a shot whose identity is only in the caption cannot.
    - **When a shot contradicts its own pass's machine-scored samples, the samples win and the shot is a bundle defect.** Per-tick DOM readings are the evidence; a picture that disagrees with them is withdrawn and said to be withdrawn inside the file — naming what it actually depicts, its md5, and why the moment could not be photographed — never quietly replaced with a better-looking one.
26. **A credentialed rendered pass runs on an isolated rig, never on the live product (2026-10-09, task `2ff1fe23`).** A pass that needs a session must be signed in on a **rig of its own** — its own port, its own database, its own throwaway credential — **built to the served tree and proven byte-identical to the served bundle by md5** before anything is read off it, so the numbers describe what the public is being served rather than a neighbour of it. The worked example already in this repository is `docs/evidence/label-per-surface-2026-10-09/`: a per-surface label register taken on a rig whose bundle was matched to the served one by md5, with the sign-in kept to the rig's own throwaway user. **Never sign in to the live product with the demo credential** (rule 10) — the demo is the surface a prospect may be shown, and a session on it is a state change on the thing we are selling. If a signed-in check on the live surface is genuinely needed, ask the lead to run it and report the result.
    This is the other half of rule 25: 25 says a screenshot must carry the identity of the page it came from; 26 says the page it came from must be a rig built to the served tree, not the served tree itself.

27. **After `git add`, read back the list you are about to commit (2026-10-09 — twice in one day).** This repo's `.gitignore` carries `*.log`, so a record's own evidence can be **silently skipped**: the 13:46 record's first commit dropped `build.log` and `seed.log`, and the same trap caught the 10:46 record's commit, where `git add cutover-20261009` skipped `cutover-seed.log` and `cutover-build.log`. Both were caught only because the author read the staged list back before submitting. Run `git diff --cached --name-only` after staging and **compare it against the files your record cites** — a commit is the last chance to notice what the ignore file swallowed. If an evidence file must be tracked despite a broad ignore pattern, stage it explicitly (`git add -f <path>`) and say so in the record.
28. **A file's name is not evidence of its contents — read the artifact's own header before you cite it (2026-10-09).** The 10:46 cutover record's raw output was rescued from `/tmp` and committed beside it, and the three files turned out to be byte-identical to the **13:46** run's — the committed evidence file's own first line read `=== cutover 2026-10-09T13:46:11+00:00 ===`. Cause: `deploy-main.sh` wrote to **fixed** paths, so each run destroyed the previous run's evidence and the earlier record's citation resolved to the **later** run's output — rule 25's mislabelled screenshot, in text. Two consequences:
    - **Evidence paths are run-stamped.** The script now writes `/tmp/cutover-<UTC stamp>-{evidence.txt,build.log,seed.log}` and prints all three when it finishes. No record may cite a fixed evidence path again.
    - **Read the artifact before attributing it.** Check its own header/identity (`head -1`, a run's own timestamp, a bundle's own `src`) rather than trusting the filename it arrived under. If a false artifact is already published, **withdraw it inside the record** — say what it actually contains, name its md5s, and state that the path it came from no longer holds that run's bytes (rule 19's language) — never quietly replace it.
29. **A revert claim is measured on the merge result, never on a two-dot range (2026-10-09 — the lead's own error, and the worst one of the day).** `git diff origin/main <branch>` compares two trees directly, so every file `main` gained **after** the branch was cut reads as a **deletion from the branch** — and a rejection written from that measurement accuses a correct PR of reverting merged work. It happened: PR #135 was sent back **twice** for "silently reverting #130" on exactly that evidence. The correct check showed `git merge-base origin/main 374ebf7` = **`6eabe5a`** (current `main`, so the branch was cut from it as its author said), a real scope of five files all under `cutover-20261009/`, and **no change at all** to the designer's file in the merge result. **The rule:** to ask whether a PR reverts something, build the merge result and diff *that* —
    `T=$(git merge-tree --write-tree origin/main <head> | head -1); git diff origin/main $T`
    — and quote that output. For **scope**, use `git diff $(git merge-base origin/main <head>) <head>` (rule 19). `git diff origin/main <head>` answers a different question — how the two trees differ — and on a branch cut before a merge it is guaranteed to lie in the direction of a false revert. A rejection that claims a revert must name the command behind it.
30. **A 200 on the public URL is not evidence the product is served (2026-10-12 — the lead's own near-miss, and the reason availability could read MET while a visitor would have seen the wrong site).** The platform supervises the *website's* dev server on this host, and at boot it claims port 3000 before anything of ours binds. On 2026-10-12 the host rebooted at 05:03:04Z, destroying both the product process and its guard; until the cutover re-claimed the port at 05:07:12Z the public URL answered **`http 200` with a placeholder page** — not the product, and not an error. Every check that only asks "does it answer, and with what status?" passed.
    **The check that distinguishes them:**
    `curl -s -o /tmp/pub.html -w '%{http_code} ' <public-url>; grep -o 'assets/index-[A-Za-z0-9]*\.js' /tmp/pub.html`
    The page must name **our** asset (`assets/index-*.js`); a placeholder page instead shows `/src/styles/app.css` and `/@tanstack-start/...` and has no `assets/index-*.js` at all. The `<title>` must read `Antum People`. The process holding 3000 must be **ours**, not `node /home/team/shared/site/node_modules/.bin/vite dev`. And a destroyed guard is invisible from outside entirely: `pgrep -af 'keep-alive'` belongs in the same check. Never report availability from a status code alone.
    **Corollary — the flag module's "noticed N late" line is a seeder artifact, not outage evidence.** A freshly seeded case whose 48-hour mark is already in the past reports a large "late" figure on the first read; on 2026-10-12 that read 29.12h and 77.12h and nearly went into the plan as a multi-day outage. It is evidence about the *seed*, never about uptime.
33. **A "PR merged" notice can be false — measure the merge result, never the notice (2026-10-12).** The platform's automation emits a "PR merged / address feedback" wrapper for reasons that do not include an actual merge; on 2026-10-12 one arrived for **#153 while the PR was open**, and the trap it sets is the mirror of rule 20's: the notice says merged, so a member "closes the loop" with an empty commit, or the team records work as landed that is not. The engineer measured it three ways and pushed nothing: the API read `state open | merged False | mergeable clean`; `git merge-base --is-ancestor <tip> origin/main` was false with `main`'s merge list naming no such PR; and the **substance was absent from `main`** (the PR's new file `docs/evidence/one-authoritative-notice-2026-10-12/host-copy-disposition.md` does not exist there, and the file that PR deletes is still present). **The specific trap: an unmerged PR can report a `merge_commit_sha`** — that is GitHub's *speculative test-merge* commit, not an object on the remote, and not evidence of anything.
    **Checks, in order:** the tip is an ancestor of `origin/main` (`git merge-base --is-ancestor <tip> origin/main`); the file the PR adds or deletes is present/absent as expected in `origin/main` (`git ls-tree origin/main <path>`); only then quote a merged SHA — and never quote one from a notice.
    **The corollary is the part that costs us:** a claim that a guard or a fix "is on main" is a claim about `main`'s **bytes**, never about a row's status or a notice. On 2026-10-12 the shipped tree carried the v2.3 notice **without** the version-consistency guard, because that guard lived only in an open PR — so nothing on `main` would have caught a partial version bump, and saying otherwise would have been false in the reassuring direction.

34. **A rejection does not stop a merge — so a rework lands on top of what merged, and must address every item (2026-10-12).** A PR the lead has sent back can be merged by the owner in parallel with the review: on 2026-10-12 the designer's re-ground was sent back for three defects (a reading block pasted three times into each of two documents, the run called "cutover 3" when it is #5, and a citation reading 2026-10-13 — a day in the future) and the owner merged it with **all three intact**. The follow-up then had to be written as a **delta on `main`**, not as a rebase of the rejected branch.
    - **After any rejection, `git fetch` and re-read `origin/main` before writing the fix.** Confirm what actually merged — the tip's ancestry (rule 33) and the substance in `origin/main`'s bytes — then base the follow-up on that state, and say in the follow-up's own body which PR it follows and what it keeps.
    - **Rule 18 still governs: a multi-item rejection is one instruction.** A follow-up that fixes one item and is *silent* about the others is a failed submission even though a PR exists. Fix them all in the same PR, or argue explicitly the ones you believe are wrong.

35.  **A rejection can arrive with no review comment at all — and a rebase under review is safe only if the tree is unchanged (2026-10-19; two failures in one round, both about the evidence a reviewer acts on).**
    - **An empty review note is not a decision that nothing was asked.** A PR sent back for a real omission arrived with the platform's review channel carrying an **empty body** (0 comments) — the instruction came as an **inbox message**. A comment count of 0 says nothing about whether the work was refused, so read the row's own status and the inbox before acting, and **ask the lead before concluding you were right** (rule 4): “there were no comments” is a report about the channel, not about the work.
    - **A rebase or force-push on a branch under review is permitted only when the content does not move, and the tree hash is how you prove it** (rule 23 forbids a moving target). Report `git rev-parse <old-head>^{tree} <new-head>^{tree}` beside the new SHA: equal trees mean the reviewer's run still describes the tree that will merge, so it needs no re-run — measured 2026-10-19, the head moved `b9ab55f` → `58e5f945` while the tree stayed `8abf849e…` on both, and a 192/192/0 verification carried over untouched. A moved SHA **with** a moved tree invalidates that verification; saying which one it is, is the author's job.
    - **Read the remote head from the remote, never from a local ref you just fetched.** Use `git ls-remote origin refs/heads/<branch>`, `/pulls/<n>` → `head.sha`, or `gh pr view --json headRefOid`. A `git fetch` with an explicit refspec writes `FETCH_HEAD` and can leave local `origin/<branch>` at the **old** head while the remote has moved — that nearly produced a suite run against a tip that no longer existed. State the head SHA you measured, so a reviewer whose number disagrees can catch it (rule 12).
36.  **A merged PR's branch is deleted when it merges — so a push to that name re-creates a branch no merge can reach (2026-10-20; the instruction was the lead's, the measurement was the engineer's).**
    - **Before pushing to a branch, check whether its PR has merged.** `git ls-remote origin refs/heads/<branch>` returning **empty** means the merge deleted it: the push would re-create that branch, and a merged PR **cannot be reopened**, so no merge can ever read the commit it lands. When it is empty, measure and **push nothing** — and say that you checked, rather than pushing because a message told you to.
    - **A change wanted after a merge gets a fresh branch off the merge commit and a new PR**, whose body names the merged PR it follows and what it keeps (rule 33's ancestry check applies). A merged record is kept true by a **dated annotation** — at its own site, or in the new material that closes it — never by rewriting it.
    - **A head that moves after review is the author's to report** (rule 35): send `git rev-parse <old>^{tree} <new>^{tree}` with the note. A reviewer told "approved" and nothing else has no way to know the verified tree is no longer the one that will merge.

37.  **Nothing maintains a local `main` — so a branch cut from the wrong base silently changes what your PR does (2026-10-20; two instances in one day, both invisible in the PR's own diff).**
    -   **Before cutting any branch:** `git fetch origin && git reset --hard origin/main`, or cut from `origin/main` directly. A branch cut from a **stale local `main`** silently reverts work that merged while you were working: your PR's diff then reads as a deletion of somebody else's landed change, and nothing in the diff says why.
    -   **A branch cut from another feature branch silently carries that branch's commits into your PR.** Measured 2026-10-20: `docs/stylesheet-30-bytes` was cut from `1d55fdc` — the head of the **#256** branch — instead of from `main`, so when **#258** merged as `9796d6b` it carried the client commit with it and **closed #256 in the same move**. #256 then read `merged: True` with its `merge_commit_sha` pointing at a commit whose message reads *"Merge pull request #258"*, and the client fix looked like it had never landed. The content was correct; the attribution was wrong — and the merge history needs the standing note that **`9796d6b` closed both #256 and #258**.
    -   **Both traps are found by ancestry, not by reading the change.** Before submitting, run `git log --format='%h %p %s' $(git merge-base origin/main HEAD)..HEAD` and satisfy yourself that every commit in it is yours and belongs in this PR. `git log <merge-base>..HEAD` names them; the PR's own diff cannot, because a carried commit's changes are already present in the tree being compared against.
    -   **A check's location is part of the check — and a control the operator cannot reach is a false green (2026-10-20).** Rule 27 was confirmed twice more on 2026-10-20: an evidence pack committed **18 of its 21 files** while `ls` still showed all 21, so the pack *looked* complete with its run, build and seed logs absent — which is why `.gitignore` now carries `!docs/evidence/**/*.log`. Two independent members hit it the same day. The pattern is not the check; **rule 27's read-back is.** The same round produced the sibling defect: a checker whose anti-vacuous control lived **only in the test runner**, so invoking its own script with a plausible flag returned a clean green run, exit 0, having tested nothing — an operator following the obvious path to re-run a control must not be able to buy a pass. When you add a control, say how someone else reproduces it, and prefer a mechanism that **fails loudly** on an invocation it did not understand.
38.  **A rejected credential is silent until a push — report it, do not work around it (2026-10-24; two cycles lost to it, and the work was already finished).**
    -   **The symptom, exactly:** `git push` → `remote: Invalid username or token. Password authentication is not supported for Git operations.` / `fatal: Authentication failed for 'https://github.com/...'`; REST and `gh` → `HTTP 401 {"message":"Bad credentials"}`. It fails the same way before and after sourcing `/etc/profile.d/cto-env-vars.sh`, and again after the stored credential file is rewritten at 09:36 — so retrying locally cannot fix it, and a re-sourced env var is not evidence of a fresh token.
    -   **What to do:** keep the work on its branch, file the patch plus the apply command only if the row's delivery needs them, and **message the lead with the verbatim error**. The lead refreshes the team's credential (`get_git_credentials`) and tells you to retry; measured 2026-10-24, the push, PR and read-back then went through unchanged — no rebase, no content change, same head SHA.
    -   **Do not:** rewrite a token locally, hunt another credential (rule 17), or push a workaround commit. The expiry is silent — the token that worked at 15:33Z on 2026-10-23 was rejected by 09:2x on 2026-10-24 — so the first sign is always a failed push, and it is the lead's to clear.

39.  **A 401 is about the credential, never about the remote — refresh the shell that pushes, then retry (2026-10-24; the fix, and the suspect that cost the time).**
    -   **The fix is a refresh, not a re-source of the env file.** In the shell that is about to push: `. /etc/profile.d/team-github.sh` (the platform's credential file; the credential-refresh tool does the same), then **retry the git command**. Measured 2026-10-25: with that file sourced the token answers the API `200` with `core.limit 5000`, and the retried push landed unchanged — same head SHA, no rebase, no content change. Sourcing `/etc/profile.d/cto-env-vars.sh` is **not** the fix: measured 2026-10-24, the rejected token behaved identically before and after sourcing it, and again after the credential file was rewritten at 09:36.
    -   **Never conclude from a 401 that the mirror, the branch or the repository is gone.** The status is about the credential, and it says nothing about the remote's contents. Measured 2026-10-24–25: the branch existed throughout, an anonymous `git ls-remote` kept answering, and the same push succeeded unchanged once the credential was refreshed.
    -   **Say plainly what it cost:** diagnostic time spent on the **wrong suspect** — the working tree, the mirror's drift, the branch — while the only thing wrong was the token. On 2026-10-24 that cost the program-manager **two cycles**, one of them a patch file a human had to land.
    -   **It is a process, not a monitor, and must not be called coverage.** Nothing in this repository can see the token: no script, suite or check detects an expired credential before a push fails — the first symptom is the failed push itself, and the block is **relayed by a person**. A plan, report or status line touching it says what is true — **relayed by hand; the first sign is a failed push** — and claims no coverage it does not have (rule 30's shape: a green that cannot redden proves nothing).
    -   **The report is one message, and it carries four things:** the **verbatim error** (rule 38's `remote:` / `fatal:` pair, or the `401 {"message":"Bad credentials"}` body), **the command that produced it**, **the state of the work** (branch, head SHA, committed or not), and **whether a patch is needed** — needed only when the delivery has to leave the member's machine. Rule 38's protocol then runs unchanged: refresh, retry, land.
40.  **A session starts with one observer run — and it is not a monitor (2026-10-26).**
    -   **The run, and what to do when it does not hold.** Before taking up the row's work, run `bash /home/team/shared/observe-serve-pair.sh` once. It is a read of the public URL — about 0.4 s, inside a session that is happening anyway — and it answers the only question that matters when this product disappears: *is the public URL serving OUR build?* If the run does not report the pair holding, **message the lead at once with the run's own output**, before starting the row's work and before diagnosing: a replacement is what that reading looks like, and the recovery is not the row's to run.
    -   **It is not a monitor, and it may never be written up as one.** Its detection exists only while a member is awake. Carry the measured number rather than a claim: member-driven detection latency across the four sessions the board's timestamps record is **19.6 h / 20.2 h / 24.6 h / 25.4 h**, and both real outages — 2026-10-25T07:13:22Z and 2026-10-26T07:58:21Z — were caught in ~1–2 minutes by **luck**, not by a check. **No KPI, plan line or status sentence may claim coverage from this rule:** the off-host check is decision 5 and does not exist yet — the priced options, their limits and the one line to rule on are in `/home/team/shared/decision-5-off-host-check-2026-10-26.md`.
    -   **A run that lands inside a movement's own restart window reads as not holding.** Every movement stops the product on 3000 and restarts it inside a run of 19–26 s, so before messaging, check whether a movement is in flight — its own log, and whether the served pair is unchanged — and say in the message which of the two you are reporting.
